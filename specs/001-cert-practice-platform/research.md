# Phase 0 研究记录

日期：2026-10-23｜输入：[spec.md](./spec.md)

## 2. 架构选择

### Decision: 模块化单体 + 无状态 AI 服务 + SPA

Java Spring Boot 承载全部业务、鉴权、持久化和管理流程；Python FastAPI 只负责模型请求。Vue 单工程通过 `/app` 和 `/admin` 分区。

**Rationale**

- 2～3 人团队无法承担多业务服务和分布式事务的维护成本。
- Java 适合事务、权限、审核和后台管理；Python 适合提示词、模型适配和生成。
- Python 无状态后，AI 失败不会阻塞非 AI 刷题，也不会形成第二套业务事实源。

**Alternatives considered**

- Next.js 全栈单体：团队已确认 Vue + Java + Python，且 Java/Python 职责清晰时可行。
- 完整微服务：当前规模没有独立扩缩容和团队边界收益，运维成本过高。
- Python 直接访问业务数据库：会产生双写、权限绕过和一致性风险。

## 3. 题目版本与内容审核

### Decision: 稳定身份 + 不可变版本 + 发布指针

`question` 保存稳定身份；`question_version` 保存正文、答案、解析、标签和状态。新版本发布时在同一事务切换 `published_version_id`，旧版本保留并记录 `superseded_at`。

**Rationale**

- 收藏和错题可以绑定稳定题目，练习和讨论绑定具体版本。
- 历史作答、成绩和讨论不受修改影响。
- 单指针比“全局最新状态”更明确，能防止多个发布版本同时被抽取。

**Alternatives considered**

- 原地覆盖：无法还原历史，违背已确认需求。
- 全量事件溯源：当前查询和团队规模下复杂度过高。
- 每个版本单独作为题目：会分裂收藏、错题和统计身份。

**Risk**

发布指针与版本状态可能不一致。通过单事务、部分唯一索引、外键应用校验和审计记录收口。

## 4. 练习快照与抽题

### Decision: 逻辑快照 + 分层配额 + 加权随机

会话保存筛选条件、规则版本、实际组成和随机种子；题目项保存版本 ID、顺序、来源和分桶。普通练习按未见/错题/普通 50/30/20 做配额和权重，难度目标默认 30/50/20。自测按原题/AI 变式 60/40，再在层内抽取。

**Rationale**

- 满足已确认的默认比例，同时允许配置和解释。
- 某层不足时可以向其他合法层回退，不会为了凑题引入未审核内容。
- 逻辑快照避免复制大段正文，又可通过不可变版本完整回放。

**Alternatives considered**

- `ORDER BY random()`：缺少权重、分桶和可测试随机源。
- 将题干答案完整复制为 JSON：重复存储并增加泄露面。
- 纯错题优先：可能连续抽到同一范围，无法兼顾未见题。

**Risk**

小题池会频繁偏离目标比例。保存实际配额和回退原因，结果页显示真实组成。

## 5. 抽题并发与提交幂等

### Decision: 短事务抽题，终态操作幂等

抽题、会话和题目项写入在同一数据库事务内完成。提交和最后一道自评使用行锁、状态前置条件和 `Idempotency-Key`，重复请求返回原结果。

**Rationale**

- 防止抽到已下线版本或双击创建多个会话。
- 练习提交、填空自评和错题更新必须原子发生。
- 结果接口可以由幂等记录稳定重放。

**Alternatives considered**

- 前端禁用按钮：不能防止重试和并发。
- 调用后覆盖成绩：破坏历史不可修改约束。
- `SERIALIZABLE` 全事务重试：当前冲突模型可以更精确地用行锁解决。

## 6. 填空判题与状态机

### Decision: 自动匹配仅作建议，自评决定最终结果

填空题目项状态：`UNANSWERED → ANSWERED → SELF_PENDING → SELF_PASSED | SELF_FAILED`。自动匹配和自评分别存储，全部自评完成后会话才进入 `COMPLETED`。

**Rationale**

- 符合低成本且可解释的需求边界。
- 自动匹配率与自评通过率可独立统计，不混淆客观和主观结果。
- 最后一道自评需要统一事务收口，避免部分完成。

**Alternatives considered**

- 自动匹配直接决定成绩：无法覆盖同义表达和原题歧义。
- 只保存最终自评：丢失自动判题质量和后续优化依据。

## 7. 认证、授权和前端职责

### Decision: 单 SPA + Java 服务端会话

浏览器只访问 Java API，Spring Security 使用 PostgreSQL 会话、HttpOnly Cookie 和 CSRF。前端路由守卫只做体验；后端验证角色和资源所有权。

**Rationale**

- 避免长期 JWT 暴露于浏览器存储。
- 禁用用户和退出登录可以集中、即时控制。
- Java 是唯一业务权威，管理端和用户端共享 API 客户端与组件。

**Alternatives considered**

- localStorage JWT：撤销、禁用和 XSS 风险更高。
- 两个前端工程：2～3 人团队维护成本高。
- 前端权限判断：不能满足安全要求。

## 8. 答案防泄漏

### Decision: 服务端状态门禁 + 独立 DTO

进行中会话只返回安全 DTO，不包含正确选项标记、规范答案、别名或解析；提交后封存答案并返回解析；题目 AI 只在会话完成且属于本人时开放。

**Rationale**

- 前端隐藏、缓存和提示词都不是安全边界。
- DTO 白名单可以从出口层避免实体字段误泄露。
- 讨论同样可能泄题，因此进行中默认隐藏本题讨论。

**Alternatives considered**

- 通过前端条件渲染隐藏答案：响应中仍可见。
- 交给 AI 提示词禁止作答：模型无法作为硬性安全控制。
- 全局禁用 AI：不能满足完成后的辅导需求。

**Risk**

用户仍可手动粘贴题目。系统明确不承诺考试级防作弊。

## 9. AI 调用与额度

### Decision: PostgreSQL 原子预留 + 唯一请求记录

个人日额度、会话轮次和团队预算使用数据库账本。请求先预占，Java 再调用 Python；成功结算实际成本，失败按策略退还个人次数并保留供应商已发生成本。

**Rationale**

- 不引入 Redis 也能满足本地和首期规模。
- 并发下由数据库唯一约束和原子更新保证不超用。
- 次数和成本分离，能处理超时和计费不确定。

**Alternatives considered**

- 内存锁：多实例或重启失效。
- 调用后记账：并发可超限。
- Redis 计数器：当前规模增加不必要组件。

**Risk**

团队预算行是热点；使用短事务、整数微美元和最大成本预留，超时请求进入人工或定时结算。

## 10. Java/Python 内部契约

### Decision: 受限内部 REST，版本化并默认非流式

Java 只传递最小上下文，Python 返回文本、结构化候选题、用量和成本。内部接口使用 `/internal/v1`、服务令牌、超时和契约测试。首期非流式请求，模糊超时不自动重试。

**Rationale**

- 避免 Python 依赖业务表和事务。
- 非流式实现更容易保证额度和成本一致。
- 首期单供应商，可通过适配器切换 Mock 和真实模型。

**Alternatives considered**

- 浏览器直连 Python：绕过额度和防泄题门禁。
- Python 直接写候选题：形成双写。
- 流式首期必做：增加断流、额度结算和消息持久化复杂度。

**Risk**

供应商可能已计费但 Java 超时。请求标记 `UNKNOWN`，不自动重试，依据供应商请求 ID 或成本上限结算。

## 11. 无 Redis/MQ 的异步生成

### Decision: PostgreSQL 任务队列

Java 创建生成批次，Spring 定时器通过 `FOR UPDATE SKIP LOCKED` 领取，租约超时后可重领。候选题先进入暂存表，审核通过后转换为正式题目版本。

**Rationale**

- 符合本地技术约束，任务状态可恢复和审计。
- Python 不持有任务事实，前端可轮询 Java。
- 候选与正式题库分离，避免两套审核事实。

**Alternatives considered**

- 请求内同步生成：耗时长、失败恢复差。
- 引入 Redis/RabbitMQ：当前规模不必要。
- pgmq 等扩展：增加部署依赖，数据库任务表已足够。

**Risk**

至少一次执行可能重复生成。使用租约、重试上限、内容哈希唯一约束和人工重试兜底。

## 12. PostgreSQL 数据与搜索

### Decision: 关系表 + 约束 + `pg_trgm`

核心关系使用普通表、外键、部分唯一索引和事务。JSONB 只用于规则快照、任务载荷和审计摘要。用户搜索使用 `pg_trgm` GIN，多标签交集使用关联表分组。

**Rationale**

- 当前 1 万题和 10 万作答规模不需要 Elasticsearch。
- 答案和解析不进入公开搜索索引。
- 唯一约束能直接保护会话去重、错题激活和额度账本。

**Alternatives considered**

- PostgreSQL 原生全文检索：中文分词效果取决于扩展，当前关键词和标签足够。
- Elasticsearch：增加部署和同步复杂度。
- 全部存 JSONB：约束、索引和审计能力不足。

**Risk**

`pg_trgm` 对长中文文本的相关性有限。先按实际查询基准调整索引，查询字段使用白名单。

## 13. 实施结论

无需未决架构问题。开发从 P1 基础闭环开始，先落地身份、目录、题目版本、练习和填空自评；任何依赖产品参数的规则都通过配置版本和会话快照处理。
